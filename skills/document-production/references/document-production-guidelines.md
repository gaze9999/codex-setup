# Document Production Guidelines

這份文件是 `Document Production` 的內部文件產出基線。它補充 `SKILL.md` 的格式與 QA 細節，不單獨作為可安裝 Skill。

## 1. 內容架構

依文件目的選擇最少且足夠的章節，不為了形式固定加入空章節。

技術／教學型文件優先使用以下閱讀順序：

1. 目的與適用範圍
2. 必要前提與核心概念
3. 架構／原理
4. 實作方式
5. 實際案例
6. 常見問題與失敗原因
7. 限制、風險與相容性
8. 模板／檢查表（有實際用途時）
9. 參考資料（有使用外部來源時）

原則：

- 概念先於細節，抽象先於具體。
- 同類實戰案例集中在同一章節或子節，不散落全文。
- 保留必要前提，但避免對進階讀者重複過多基礎內容。
- 以易理解為主; 流程或責任適合時用 Mermaid, 比較用表格, 只有操作能幫助理解且交付格式支援時才用互動視覺化; 簡單內容使用文字, 不為裝飾加圖
- 長篇文件維持一致的章節層級與術語。
- 避免重複、空泛、偏題與與文件目的無關的內容。
- 避免「不是 OO，而是 XX」及同類二分對照句式。

## 2. 檔名與版本

### 檔名

- 簡潔、可辨識、偏學術／技術文件命名。
- 使用主題名稱，不把文件版本塞進檔名。
- 同一內容的不同格式使用相同 basename，例如：
  - `Coding_Agent_Prompt_Engineering_Tutorial.pdf`
  - `Coding_Agent_Prompt_Engineering_Tutorial.docx`
  - `Coding_Agent_Prompt_Engineering_Tutorial.md`

### 文件內版本資訊

- 只有使用者、來源或交付流程要求時才標示文件版本或程式版本，不為一般文件自行建立版本制度。
- 沿用已提供的版本格式與遞增規則；沒有明確規則時先保留既有格式，不自行假設 `v1`、Semantic Versioning 或固定碼數。
- 程式版本無法確認或文件不涉及程式時省略，不填 `unknown` 佔位，也不寫入推測版本。

## 3. 目錄

長文件或多層章節文件建立目錄時：

### DOCX

- 標題使用 Word 原生 Heading styles。
- 使用 native TOC field，不手動維護頁碼。
- 目錄標題靠左。
- 頁碼靠右並使用 dot leader / tab stop。
- 設定 `updateFieldsOnOpen=true` 時，仍必須以 render 後的實際頁面驗證 TOC。
- 最終 QA 檢查每個 TOC entry 是否對應正確 heading 與頁碼。

### PDF

- PDF 內顯示的目錄頁碼必須依最終排版結果確認。
- 不直接沿用未更新的 DOCX field 結果。

### Markdown

- 使用 heading hierarchy 作為主要導航。
- 只有文件長度與用途需要時才加入 Markdown TOC。
- 不加入虛構頁碼。

## 4. 分頁與版面

### Heading

- 標題不得孤立在頁尾而內容移到下一頁。
- 優先將 heading 與至少一段後續內容保持在同頁。
- 避免 widow / orphan layout。

### Tables

- 表格若能完整放在同頁，避免跨頁。
- 只有表格本身長度超過一頁時才接受跨頁。
- 多頁表格重複 header row。
- 不讓單一資料列被不必要切斷。
- 欄寬以可讀性為優先，不為塞入同頁而把文字壓到不可讀。

### Diagrams / figures / code blocks

- 圖表與其標題／說明盡量保持在同一頁。
- 程式碼與邏輯區塊避免從中間不必要拆頁。
- 若物理尺寸確實超過單頁，採合理拆分並保留上下文。

### Whitespace

- 保留必要留白提高閱讀性。
- 避免因錯誤 page break、keep-with-next 或表格設定造成半頁以上無意義空白。

## 5. PDF

- PDF 為未指定格式時的預設輸出。
- 優先保留真正的文字內容，避免把整頁 rasterize 成圖片。
- 確保繁體中文、日文、英文與文件中實際使用的符號皆正常顯示。
- 可行時使用適合分享的字型處理方式，避免收件端缺字型造成版面破壞。
- 最終 PDF 必須以 render 結果檢查，而不能只檢查產生程式沒有報錯。

逐頁視覺 QA 至少檢查：

- 標題是否被切斷或落單
- 目錄頁碼
- 表格跨頁
- 圖片與 caption
- 頁首頁尾
- 字型／缺字／亂碼
- 超出頁面邊界
- 大量異常空白
- 頁碼連續性

## 6. DOCX

- 使用原生 Word 結構，不用純視覺模擬取代可編輯結構。
- Heading 使用 Word styles。
- TOC 使用 native TOC field。
- 頁碼使用 `PAGE` / `NUMPAGES` fields。
- 需要自動更新時設定 `updateFieldsOnOpen=true`。
- 動態 field 只是更新機制，不等於最終 pagination QA。
- 表格需要時設定 repeat header row。
- 使用 keep-with-next / keep-together 等機制時需避免造成過度空白。

最終 DOCX QA：

1. 結構檢查：heading、TOC、fields、tables、relationships。
2. 若能 render，檢查 Word／PDF 實際頁面。
3. 驗證目錄中的頁碼與實際 heading 位置。
4. 若無法 render，交付時明確標示未完成視覺 QA。

## 7. Markdown

- 內容結構以標準 heading hierarchy 表達。
- 不使用 PDF／DOCX 專屬排版假裝固定頁面。
- 表格只在文字量與欄位數適合 Markdown 時使用；過度複雜的表格改用較清楚的章節或清單。
- 程式碼使用正確 language fence（可確認語言時）。
- 同一文件若同時輸出 PDF / DOCX / Markdown，事實內容與引用保持一致。

## 8. 引用與資料來源

- 每個外部來源必須直接支持對應敘述。
- 技術內容優先：官方文件、標準、原始技術資料。
- 學術內容優先：原始研究、系統性回顧、Meta-analysis、正式學術來源。
- 涉及科學、醫療、健康、藥學、心理學或其他以專業研究證據為基礎的領域時，必須使用 APA 第七版引用格式。
- APA 第七版至少包含適當的文內引用與文件末尾完整參考資料清單。
- 有 DOI 時必須提供 DOI；可確認正式出版資訊時，不使用不完整二手資訊取代。
- 重要事實、統計數據、實驗／臨床結果、風險效益結論與具有爭議性的專業主張必須有可追溯來源支持。
- 不使用內容不符、已失效、無法確認或純二手轉述來源作主要證據。
- 區分已確認事實、合理推論、假設條件與尚無法確認內容。
- 不能把統計相關性寫成因果，也不能把理論機制寫成已證實臨床效果。

## 9. 多格式一致性

若同時產出多個格式：

- 先建立同一份 canonical content。
- PDF、DOCX、Markdown 共用相同章節、數字、專有名詞、來源與結論。
- 只允許格式特有的呈現差異，例如 PDF/DOCX 分頁、DOCX field、Markdown heading。
- 最終檢查不同格式是否因轉換造成段落遺漏、表格資料遺失、引用漂移或版本資訊不一致。

## 10. 最終 QA 狀態

交付時只能使用下列狀態描述：

- `通過`：實際完成並符合要求。
- `失敗`：已執行但結果不符合要求。
- `未執行`：環境或任務不需要執行。
- `未驗證`：產物存在，但缺少可用的 render／檢查能力或其他必要條件。

不得把「檔案成功建立」直接等同於「版面 QA 通過」。
